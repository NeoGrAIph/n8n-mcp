# Synestra Platform: n8n-workflows as code (dev/prod)

Этот документ описывает **к чему привел** GitOps-подход для разработки workflow n8n в платформе Synestra.
Он специально не углубляется в детали манифестов/Helm/Argo CD. Если нужно проверить реализацию или найти точные файлы,
ориентируйтесь на репозитории платформы и workflow-артефактов.

## Результат GitOps-подхода

1. Workflow n8n и код из Code/Set(raw) нод материализуются в файлы и живут как артефакты в отдельном репозитории `n8n-workflows`.
2. Есть **две ветки/две рабочие копии (worktree)**:
   - `dev` (ветка `main`) для разработки и быстрой проверки.
   - `prod` (ветка `prod`) для фиксации боевого состояния.
3. Dev и Prod отличаются не “политикой git”, а **потоком изменений**.

## Dev: двунаправленная синхронизация (UI/API <-> files)

Dev-контур устроен так, чтобы разработка workflow была похожа на DevOps-цикл:

- Изменения в UI/API n8n-dev приводят к обновлению файлов в `n8n-workflows/dev/workflows/**`.
- Изменения в файлах (в первую очередь code/set файлы) автоматически применяются обратно в n8n-dev через API.

Практический эффект:
- можно править Code/Set(raw) как обычный код в редакторе;
- получать быстрый feedback (workflow выполняется в n8n-dev);
- затем фиксировать “качественный результат” коммитом в ветку `main`.

Что обычно коммитится:
- JSON workflow (`workflows/<folder_path>/<workflow_id>.<slug>.json`)
- файлы узлов (`workflows/<folder_path>/code_nodes_<workflow_id>/*.py|*.json|*.set.json`)

Что обычно **не** коммитится (runtime state):
- `*.hash`, `*.dat`
- каталоги `.index/`, `.archived/`

(Эти правила обычно зафиксированы в `.gitignore` репозитория `n8n-workflows`.)

## Prod: однонаправленная синхронизация (UI/API -> files)

Prod-контур сделан консервативно:

- Файлы в `n8n-workflows/prod/workflows/**` являются **проекцией** боевого состояния (экспорт из DB через цепочку платформы).
- Автоматического применения изменений из файлов обратно в n8n prod нет.

Практический эффект:
- исключается риск “случайной правки файла”, которая немедленно влияет на прод;
- изменения в prod выполняются контролируемым шагом (обычно через API), после чего экспорт обновляет файлы;
- затем состояние фиксируется коммитом в ветку `prod`.

## Как n8n-mcp вписывается в этот подход

`n8n-mcp` имеет отдельный класс инструментов — **workflow files tools**, которые работают с файловым слоем.

В платформенном деплое часто делается так:
- `N8N_WORKFLOWS_ROOT` монтируется на каталог `n8n-workflows/dev/workflows`.

Это означает:
- по умолчанию операции чтения/патча файлов через MCP направлены на **dev-артефакты**;
- чтобы обслуживать `prod` файловый слой через MCP, обычно нужен отдельный деплой/конфигурация с другим mount/root.

## Где смотреть источник истины по реализации

- Платформа (GitOps, PV/PVC, экспорт/вотчер, Argo CD ownership): репозиторий `synestra-platform`.
- Артефакты workflow (ветки `main`/`prod`, правила коммита/переноса): репозиторий `n8n-workflows`.
